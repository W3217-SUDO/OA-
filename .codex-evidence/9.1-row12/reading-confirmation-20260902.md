## 新系统源码/数据差异审计

- `POST /api/v1/tasks` 的案件任务持久化状态必须是 `待处理`；`GET /api/v1/tasks?relation=owned` 直接按工作流状态分栏。
- `relation=initiated` 与案件详情任务列表仅对未接受的案件任务把关系视图显示状态映射为“处理中”，同时保留 `workflow_status=待处理`；计时来自创建/开始/截止时间，不依赖负责人是否已接受。
- `POST /api/v1/tasks/{id}/accept` 仅允许负责人本人把 `待处理` 迁移为 `处理中`，并写入工作流历史。
- 上一轮误判是把发起人关系视图的“已发出/开始计时”显示语义直接下沉为全局持久化状态，导致负责人绕过接受动作。

## 原要求逐项映射

1. 负责人不要直接进入进行中 → 当前错误图负责人待处理为 0 → 旧图待处理有记录 → 创建后用独立负责人账号确认待处理计数与任务行。
2. 接受后才能进行中 → 旧图提供接受按钮，旧控制器按节点迁移 → 勾选同一任务接受，确认待处理 -1、进行中 +1、历史落库。
3. 发布即开始计时 → 发起人关系视图和时间字段独立于负责人工作流状态 → 创建后立即确认剩余时间，刷新不丢失。
4. 发起人与负责人界面不强制相同 → 同一持久化 `workflow_status=待处理`，发起人关系视图可显示进行中、负责人视图显示待处理 → 分别以两个账号验收同一记录。
