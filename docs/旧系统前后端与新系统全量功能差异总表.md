## 用途与判定口径

本表是后续集中整改的唯一问题台账。审计必须同时核对：

1. 旧前端 `cshtml` 中的页面、查询条件、按钮、弹窗、明细和显示条件；
2. 旧前端 JavaScript 中的请求地址、参数、成功/失败处理和后续刷新；
3. 旧后端 Controller/Action 及反编译业务方法中的权限、状态、数据和文件处理；
4. 新 React 页面中的真实入口、可见条件、上下文传递和后续联动；
5. 新 FastAPI 接口中的鉴权、校验、事务、落库、文件生成、日志和状态同步；
6. 页面点击、API 冒烟、数据库/附件结果及精确清理证据。

只存在菜单、页面骨架、弹窗或成功提示，不算功能完成。旧源码中的备份页面、重复 Area、
第三方组件和没有有效页面入口的内部 Action，不机械计入业务缺口；必须先确认它属于旧系统真实可用业务。

状态仅使用以下三类：

- **确认缺失/不一致**：旧前端入口和旧后端真实处理均有证据，而新系统缺入口、缺接口或行为不同；
- **已实现待证明**：代码存在，但尚未证明权限、状态、落库、文件或跨页面同步全部正确；
- **已验证闭环**：已获得页面行为、接口结果、数据结果和清理证据，不再重复验收。

- **旧前端与后端证据**：旧系统 `Areas/IPR/Controllers` 具有独立的 `PatentCaseListController.cs`、`TrademarkCaseListController.cs`、`CaseController.cs`、`CPCController.cs` 及专利/商标官文、官费、发票文件控制器。`CaseController.cs` 明确实现案件年费年度、费率、期限、协作费、律所协作、文件解锁/标签转换/对冲、多案件创建、重新开启、专用 Word 导出与文件批量导入等动作；这些不是普通民事案件字段的简单展示。
