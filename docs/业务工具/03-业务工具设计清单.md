# 业务工具设计清单（31 个，已实现并本地测试，待陶威确认后上线）

目标：按 PPT 的业务动作做工具——**一个业务动作 = 一个工具**，内部组合多个原接口；智能体不用再自己“找接口→查定义→拼 data→逐个调用”。

## 共同规则

1. **不绕过权限**：每个内部步骤都走现有 MCP 调用通道（`call_tool`），即用当前登录人/个人令牌身份调用原接口；原接口的角色权限、数据范围、字段校验、审批流照常生效；个人令牌的“只读/可写”“业务范围”限制照常生效；每步都记操作日志。
2. **写操作两段确认**：写工具有 `confirm` 参数。
   - 不传或 `confirm=false`：只做查询和核对（找到哪个客户/合同/案件、要调用哪几个接口、填什么值、缺什么），**不写任何数据**，返回“执行计划”给用户看。
   - 用户同意后带 `confirm=true` 再调用才真正执行。
3. **不可撤回的步骤**（审批、盖章、付款核销、开票/作废、退费到账）照旧只生成“待确认请求”，须本人在 OA 网页确认。
4. **中途失败**：停在失败那一步，返回已完成的步骤和结果（含新建记录 ID），不自动重试、不自动回滚（每步变更都有留痕，可由管理员还原）。
5. 命名：`biz_` 开头；读工具标“读”，写工具标“写”。
6. 暴露位置：OA 内智能体（DSH 工作区）和个人令牌 MCP（外部智能体）都提供；令牌只开放所选业务范围内、且其全部内部接口都允许的工具。

## 不做成业务工具的（保持原样或网页办理）

- 客户服务端开通（账号密码）——不开放给智能体。
- 银行到账 Excel 导入、公证书文件/发票文件批量导入——原接口已是一步（上传附件 ID 后调用导入接口），不再包装。
- 各类审批结论（合同审批、请款审批、归档审核、开票、核销）——仍由原接口生成待确认，本人网页确认。

## 实现方式（确认后做）

- 后端新增 `apps/api-server/app/agent_mcp/business_tools.py`：每个工具一个函数，内部只通过 `call_tool` 调原接口；`confirm=false` 时只跑读接口、生成计划。
- 在个人令牌 MCP（`gateway.py`）和 OA 内智能体（`model_tools.py`）注册这些工具；个人令牌按“业务范围 + 只读/可写”过滤。
- 测试：每个工具的计划模式、执行模式、权限不足（无写权限、业务范围外、非本人数据）都要有用例；用本地库 + `CODEX-*` 测试数据跑一遍，跑完清理。

## 实现与测试结果（2026-10-30）

- 代码：`apps/api-server/app/agent_mcp/business_tools.py`（31 个工具）；注册在 `gateway.py`（个人令牌 MCP）和 `model_tools.py`（OA 内 DSH 智能体）；使用指南 `usage_skill.py` 增加“先看业务工具、写工具两段确认”。
- 个人令牌连接选了业务范围（`?biz=`）时，业务工具只有在它用到的**全部**接口都在所选范围内时才出现（不扩大令牌范围）。很多工具会用到通用记录查询（第 25 组），所以选业务的连接要加 `workbench`；不选业务的连接能看到全部业务工具。
- 端到端测试 `tests/regression/agent_mcp_business_tools_e2e.py`（真实应用 + 隔离 SQLite + 登录 + 个人令牌 + `/api/v1/mcp`）：50/50 通过。覆盖：客户新建（计划不写库、执行后可查）、客户编辑、利益检索、合同新建+附件+提交审批、合同总览、合同变更计划、从合同建案（含当事人、完成新建）、案件总览、补三要素、新增费用、法院退费、申请开票/合同付款/归档的计划、发布调查任务、子任务、新增线索并提交、我的线索、线索审核（生成待网页确认）、取证登记、线索生成案件计划、任务留言/拒绝须写理由、回款登记、控制台/请款单/到账/待结算查询、参数校验、业务范围过滤、普通账号只读令牌看不到写工具且调用被拒、普通账号看不到别人的客户（数据范围保留）。
- 结构测试 `tests/regression/agent_mcp_business_tools_test.py`：内部只调用声明过的目录接口、写工具都有 confirm、计划模式不调用任何写接口、旧系统失败包会中止、只读令牌与业务范围过滤。
- 未在测试库里跑通“执行”的：合同付款、合同/案件开票（测试库里没有已到账的律师费可开）、回款分配、申请结算、提交归档——只验证了计划模式和候选查询；上线前建议在生产用真实单据走一遍计划模式（不写数据）核对。
