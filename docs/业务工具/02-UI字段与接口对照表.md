# UI 字段 ↔ MCP 接口对照表

- 步骤编号对应 `01-PPT业务清单.md`。
- **UI 字段**写法：`新系统表单标签=参数名`，`*` 为必填。标签取自 `apps/admin-web/src` 的实际表单（PPT 截图是旧申浩界面，名称基本一致，差异处已注明）。
- **接口**是 OA MCP 目录（由后端实际路由自动生成，共 878 个工具）里的工具名与路径；`body.data.x` 表示字段放在请求体 `data` 对象里。
- **结论**：✅ 对上（2026-10-30 已在接口层对齐 G1–G12，见末尾）；🔒 有意不开放（G5、G7）。
- 对齐方式均向后兼容：网页原来的请求写法（字段放在 `data`、先建记录再上传附件）继续有效。

## 缺口清单与接口层对齐结果（2026-10-30）

| 编号 | 原问题 | 接口层怎么对齐的（向后兼容） | 状态 |
|---|---|---|---|
| G1 | 合同、线索、客户编辑的大部分字段在自由对象 `data` 里，接口定义没列键名 | `data` 在 schema 里列出全部已知键（类型、中文说明、枚举），MCP 原子工具可见；新增同名顶层具名参数，服务器归并进 `data`；与 `data` 同键不一致时 422。涉及：POST /contracts、PATCH /contracts/{id}、POST/PATCH /investigations/records、PATCH /customers/{id}、POST /customers | ✅ |
| G2 | 合同新建用 `data.type`，变更用 `contract_type` | 新建也接受 `contract_type`（归并为 `data.type`，旧写法照常） | ✅ |
| G3 | 调查任务“授权范围/授权区域”与 `region`/`authorization_scope` 名字交叉 | 新增含义一致的 `authorization_range`（授权范围）、`authorization_area`（授权区域）；旧名继续有效，说明写清 | ✅ |
| G4 | 上传须先建记录再上传 | 新建合同/线索/客户/案件可直接带 `attachment_ids`（本人上传、未关联业务的附件）；建前先核对，建后复用原上传入口挂接（权限、类别、案件自动化不变）；两步方式保留。导入类接口本身就是 files 传附件 ID 一步完成 | ✅ |
| G5 | 客户服务端开通（账号密码）不在 MCP 目录 | — | 🔒 有意不开放 |
| G6 | 建案是 建案+当事人+司法 三个接口 | 新增 POST /cases/create-complete 一步到位（逐步沿用原入口权限校验；中途失败返回 case_id 与已完成步骤，勿重复新建） | ✅ |
| G7 | 审批、盖章、付款核销、开票作废、退费到账只生成待确认 | — | 🔒 有意不开放（须本人网页确认） |
| G8 | judicial 只在建案时可用，建案后报“请先完成当事人信息” | 建案后调用改为明确 409：“案件已完成新建…请用 PUT /cases/{case_id}/court-info”；两接口的分工写进 schema 和操作说明 | ✅ |
| G9 | 旧接口业务拒绝时回 HTTP 200 + `IsSuccess:false` | MCP 层统一转为失败（409，带原 Message 和原返回）；网页仍收到原来的 200 包，前端不受影响 | ✅ |
| G10 | 前置条件只在报错里 | 合同提交（须有合同附件、审批人须在名单）、按合同建调查任务（合同非草稿、须配置调查主管）、建案三步、批量修改（须已通过立案审批）、court-info 等写进参数说明和操作说明（MCP 原子工具的 usage/prerequisites/limitations） | ✅ |
| G11 | 组织类型、客户诉讼地位等固定值没写枚举 | schema 写入枚举：组织类型、客户诉讼地位、案件类型；合同主体限 律所/平台；合同类别、收费模式列出常用值（后端原本不限，保持不限） | ✅ |
| G12 | 线索状态参数格式和名称不统一（“待审核”实为“待审批”） | `statuses` 说明写明逗号分隔和全部实际状态；接受页面名称别名：待提交=草稿、待审核=待审批、已拒绝线索=已驳回+已拒绝、已取证线索=已取证+已转案件 | ✅ |
