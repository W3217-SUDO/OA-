# 整改 Markdown 标准模板与示例

## 使用规则

- 每个清单问题单独建立一份文档，推荐文件名：`<工作表>-第<行号>行-整改定位.md`。
- 原文、补充说明和返工文字必须逐字保留；截图逐张编号分析。
- 原有功能整改先完成旧系统实现、新系统实现、差异和根因，再填写修改清单。
- 新增功能或独立新需求且旧系统没有对应能力时，不执行旧系统对照：“旧系统实现”填“不适用：新增需求，旧系统不存在”，“新旧差异和根因”改为“需求与当前实现差距”，表格的“旧系统行为”列改为“用户要求”。依据完整原文和当前架构定位后填写修改清单，不索取或伪造旧证据。
- 修改开始后逐项更新复选框。发现新范围时先更新本文档，再改代码。
- 路径、函数、接口、表和字段必须填写真实名称，不得写“相关代码”“相关接口”。

## 脱敏填写示例

以下仅示范定位深度，业务名称和代码名均为虚构：

```markdown
# 9.2第15行整改定位

## 1. 清单原文
- 工作簿：问题清单.xlsx
- 工作表：9.2
- 行号：15
- 原始问题（逐字）：转交任务时无法选择接收人。
- 补充说明（逐字）：无
- 返工意见（逐字）：输入姓名后没有候选人员，且缺少转交时间。
- 当前状态：返工定位中

## 2. 截图分析
### 图 1：转交任务弹窗
- 所属页面/入口：事务中心 > 我接受的任务 > 进行中 > 转交
- 业务对象和可见数据：任务编号已选中；接收人为空
- 涉及功能：任务转交
- 涉及按钮/字段：接收人、转交时间、确定
- 用户标注区域：接收人输入框
- 截图显示的实际异常：输入姓氏后没有人员候选；页面没有转交时间字段
- 与其他截图的关系：旧系统截图显示接收人下拉和转交时间

## 3. 旧系统实现
- 入口、角色和数据状态：任务承办人打开进行中任务
- 页面载体和布局：右侧任务详情中的转交表单
- 操作步骤与按钮行为：点击转交，选择组织人员和时间后提交
- 字段默认值、展示和校验：接收人必须来自在职人员；时间必填
- 状态流转及下游结果：写入新承办人并生成转交记录
- 数据表、字段及关联：任务 assignee_id 关联用户 id；转交记录保存 effective_at
- 采用证据：旧页面截图图2；旧控制器 `TaskController.transfer`

## 4. 新系统当前实现
### 前端
- 页面和入口：事务中心 > 我接受的任务 > 转交弹窗
- 文件：`src/pages/TaskCenter.tsx`
- 组件/函数：`TransferDialog`、`submitTransfer`
- 状态、事件和 API 调用：接收人使用普通 Input，直接提交姓名字符串到 `/api/tasks/{id}/transfer`
- 当前行为形成原因：没有调用人员搜索接口，也没有转交时间状态

### 后端
- 文件：`app/routes/tasks.py`
- 路由：`POST /api/tasks/{id}/transfer`
- 服务/权限/校验函数：`transfer_task`
- 持久化及下游逻辑：按姓名查首条用户后直接更新 assignee_id
- 当前行为形成原因：请求模型没有 receiver_id 和 effective_at

### 数据库
- 表：`business_records`、`workflow_events`、`users`
- 主键/软关联字段：任务 data.assignee_id -> users.id
- 状态/权限字段：users.status、任务 data.status
- 查询或写入关系：按姓名模糊匹配会产生重名歧义
- 历史数据兼容：既有转交事件可能没有 effective_at，读取时需允许为空

## 5. 新旧差异和根因
| 编号 | 具体页面/数据/功能/按钮 | 旧系统行为 | 新系统行为 | 证据 | 根因 |
|---|---|---|---|---|---|
| D1 | 转交弹窗接收人 | 组织人员下拉，提交用户 ID | 普通文本框，提交姓名 | 新旧截图及源码 | 前端控件和后端请求模型未按人员 ID 设计 |
| D2 | 转交时间 | 必填并写入转交记录 | 字段缺失 | 旧截图及接口源码 | 前后端均未实现 effective_at |

## 6. 精确修改清单
- [ ] M1 前端 `src/pages/TaskCenter.tsx::TransferDialog`：改为远程人员 Select，保存 receiver_id；对应 D1。
- [ ] M2 前端 `src/pages/TaskCenter.tsx::TransferDialog`：增加必填时间控件；对应 D2。
- [ ] M3 后端 `app/routes/tasks.py::TransferRequest/transfer_task`：按用户 ID 校验在职状态，并保存 effective_at；对应 D1、D2。
- [ ] M4 数据库：不新增字段，effective_at 写入现有 workflow_events.payload；对应 D2。
- 影响范围与回归风险：待处理和进行中任务共用弹窗，需同时回归；历史事件读取允许字段为空。

## 7. 验证清单
- [ ] 同姓、重名、离职人员的人员搜索测试
- [ ] 缺少接收人或时间时返回明确错误且任务不变
- [ ] 转交成功后刷新仍显示新承办人和转交时间
- [ ] 前端生产构建
- [ ] 清理测试任务、事件和账号
```
