# 钉钉在线问题排查流程

本流程服从主 SKILL.md 开头的 P0：每次只输入“当前行完整原文及补充/返工原文＋一张实际截图”，完成该图定位并落盘后再读下一张，本行全部完成后再进入下一行。所有批量准备均不得变成批量视觉输入。

用于“查看钉钉在线表格的问题”“处理某日期工作表未标记 1 的行”“按在线清单整改”等请求。与 `problem-remediation` 主流程一起执行。

## 1. 定位在线表格

1. 使用钉钉电子表格能力读取文档元数据和工作表列表，记录文档 ID、文档名称、工作表 ID、工作表名称和读取时间。
2. 用户给出日期时，按工作表名称精确匹配，例如 `9.4`；不要把文档修改日期、截图日期或相邻工作表当成目标。
3. 用户给出行范围时读取该范围，并额外读取表头行。用户说“没有 1 的行”时，先确定完成状态对应的实际列，再读取数据区全部已用列和全部候选行。
4. 不控制 Codex 内置浏览器。除非用户明确要求浏览器自动化，否则通过钉钉表格接口读取，页面验收留给用户。

## 2. 完整读取

对每一行从首个已用列读到最后一个已用列，至少记录：

- 模块、问题原文、补充说明；
- 原系统说明、新系统说明；
- 整改意见、返工原因、返工备注、验收备注；
- 完成状态及其原始值；
- 超链接、批注、公式显示值和后来新增的列。

保留原始文本，不纠正错别字、不合并相似行、不先写根因。长文本必须完整保存到行级整改 Markdown。

## 3. 图片与附件

1. 枚举目标范围内全部浮动图片、单元格图片和附件。
2. 根据锚点建立唯一映射：`图片 -> 工作表 ID/名称 -> 行号 -> 列号 -> 表头`。
3. 下载到批次证据目录，文件名包含行号和列号，例如 `row15-col4-old-system.png`。
4. 每次携带该行完整原文，只查看一张图的标注区域、页面标题、业务数据、按钮、弹窗/抽屉和错误提示；完成本图分析、必要源码定位及持久化记录后，才可输入下一张。不得一次输入同一行多张图。
5. 图片只是证据。旧系统实现以可执行旧源码、旧数据关系和可复现行为为权威；无法确认的截图细节标记为“参考，待源码/数据验证”，不能据此编造规则。
6. 图片归行与证据角色必须分别确认。对每张图登记可见页面标题/菜单、业务对象、按钮或弹窗标题作为视觉身份指纹，并标注“新系统现象/旧系统目标/返工未通过”。不得用文件名、图片顺序、所在列名或截图外观相似度直接分类。
7. 图片清单完成后做反向核对：按行检查锚点坐标、图片数量、文件名和视觉身份是否一致；发现串行、漏图、同图多归属或新旧角色无法从画面确认时，暂停定位并补证据，不能开始代码修改。
8. 保存可复核 manifest，至少包含 `image_id、sheet_id/name、row、col、header、filename、sha256、evidence_type、新旧/返工角色、mapping_status`。无锚点、跨合并单元格或行号不确定时标记“不确定”，整批停在定位阶段。

## 4. 未完成行判断

- 只有完成状态单元格的规范值明确为 `1` 或用户约定的“已验收”值，才视为完成。
- 空值、`0`、返工、待处理、待验收、测试失败以及含失败备注的行都属于候选问题。
- 状态列为 `1` 但同一行返工列记录失败时，不得直接跳过；列为状态冲突并交给用户确认。
- 排查和部署完成不能自动写 `1`。只有用户完成页面测试并明确确认通过后才能更新。

## 5. 本地证据快照

在证据目录保存：

```text
<日期或工作表>/
|-- source-snapshot.xlsx
|-- row-<n>-reading-confirmation.md
|-- row-<n>-remediation.md
|-- batch-location-summary.md
`-- images/
```

导出可用时保存在线表格快照；不可导出时保存结构化读取结果和文档/工作表标识。证据目录不得包含登录凭据或访问令牌。

每个批次还应保存 `image-manifest.json` 或等价 Markdown，以及按行逐图分析记录；不要求生成 contact sheet，禁止将拼图作为模型定位输入。manifest 是后续返工的唯一图片索引；文件名和截图顺序只能作为展示信息，不能作为归行依据。

JSON manifest 可用 `scripts/validate-screenshot-manifest.py` 校验。需要对齐旧系统时使用 `--require-old-new`；仅对实际附有返工截图的行取单行 manifest 使用 `--require-rework`，不能让只有返工文字的行因缺图被误判。校验失败必须停在定位阶段。

## 5.1 单问题等质检查

在线多行排查完成后，对每一行分别回答以下问题。全部为“是”才允许把该行纳入整批实施：

```text
[ ] 完整原文、返工文字、批注和全部截图是否可独立还原该问题？
[ ] 每张截图是否唯一归行，并具体识别页面、数据、功能、按钮和标注区域？
[ ] 是否找到旧系统同一入口、角色、状态和数据关系，而非只看截图外观？
[ ] 是否追踪新系统前端事件/API、后端路由/服务/权限/事务和数据库关系？
[ ] 是否枚举所有能产生该状态或动作的真实页面/API 入口？
[ ] 测试夹具中的人员、部门、权限、状态和关联数据是否在线上可能真实成立？
[ ] 是否为该行建立独立的根因、修改映射、聚焦测试、失败路径和清理方案？
[ ] 是否为最新原文及返工要求逐项列出预期结果、应排除的数据、所属账号、列表与计数口径，以及实施后的验证方案和待用户页面验收项？
```

其中任何一项为“否”，该行仍处于定位中。不能因为其他行已清楚或共享代码已找到而提前修改。

## 6. 单行确认单模板

```markdown
# <工作表> 第<n>行定位确认

## 表格身份与原文
- 文档/工作表/行号：
- 完整列读取：
- 问题原文：
- 补充/返工/验收文字：
- 当前完成状态：

## 图片逐项分析
- 图片及锚点：
- 画面视觉身份指纹：页面标题/菜单、业务对象、标签页/弹窗、按钮组合：
- 页面/数据/功能/按钮观察：
- 证据性质：新系统现象 / 旧系统参考 / 返工证据
- 映射状态：已确认 / 不确定（不确定时不得实施）
- 与同一行其他图片的关系：前后步骤 / 新旧对照 / 失败复现 / 独立证据
- 图片映射审计：原始文件名、OOXML anchor、row/col/header、sha256、evidence_type、配对图 ID、复核时间、冲突与处理：
- 旧流程步骤对照表：step-1…n 的页面载体、标题、字段、按钮、校验、结果，以及新系统对应入口和缺失项：

## 旧系统权威实现
- 页面入口和角色：
- 前端模板/按钮行为：
- 控制器/服务：
- 数据表、字段、关系和状态：
- 无法确认项：

## 新系统当前实现
- 前端组件/状态/API调用：
- 后端路由/服务/权限/事务：
- 数据库模型/关联/历史兼容：

## 具体差异与根因
- 页面：
- 数据：
- 功能：
- 按钮：
- 根因：

## 修改清单
- 文件/函数/接口/字段：
- 预期结果：
- 影响范围与共享入口：

## 验证清单
- 聚焦测试：
- 相邻回归：
- 持久化/失败原子性：
- 生产构建：
- 数据清理：
- 用户验收动作：
```

## 7. 整批汇总模板

```markdown
# <工作表> <行范围> 整批定位汇总

| 行 | 模块与页面 | 原始现象 | 旧系统权威行为 | 新系统偏差 | 根因 | 修改范围 | 依赖/冲突 |
|---|---|---|---|---|---|---|---|

## 共享修复
- 可复用的接口、权限、组件或数据规则：

## 独立修复
- 不能合并处理的行及原因：

## 共享改动矩阵
| 共享文件/服务/数据关系 | 涉及行 | 唯一编辑所有者 | 一次性改动 | 每行验收映射 | 交叉回归 |
|---|---|---|---|---|---|

## 联合测试矩阵
| 行 | 独立聚焦测试 | 真实入口矩阵 | 生产数据假设 | 失败/事务路径 | 相邻与跨行回归 | 清理 |
|---|---|---|---|---|---|---|

## 确认门禁
- 已读取全部列：是/否
- 已归档全部图片：是/否
- 已完成旧/新源码与数据定位：是/否
- 每行已达到单问题等质标准：是/否
- 已建立共享改动与联合测试矩阵：是/否
- 已按最新线上列值和图片锚点复核，变更行重新定位与验证：是/否
- 等待用户确认后再修改：是
```

## 8. 示例

用户请求：“查看 9.2 工作表没有 1 的行。”

正确处理：先读取 `9.2` 的表头、全部已用列和状态列；筛出空值/返工行；逐行下载并归档图片；把“案件中心”进一步定位到具体列表或详情标签页、记录关联键、接口和按钮；追踪旧系统源码与新系统实现；逐行通过单问题等质检查；生成每行确认单、共享改动矩阵、联合测试矩阵和整批汇总；用户确认后统一修改、统一联测并一次发布。

错误处理：只看问题列；只看截图文字；把相邻页面当目标页面；看到状态为空就直接写代码；修改一行就部署一次；自动把状态写成 `1`。
