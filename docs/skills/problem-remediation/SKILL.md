# OA 问题整改

## 每次前端修改必须同时完成手机适配

- 所有前端新增、整改、返工和样式修改都必须把桌面与手机适配作为同一交付范围，即使用户只提供桌面截图，也不能把手机适配留到以后。
- 修改前必须读取 [前端手机适配检查](references/frontend-mobile-adaptation.md)，追踪实际断点与样式生效链路；修改后核对实际构建样式在窄屏下的布局、长文本、数字、图标、触摸区域及固定导航遮挡。仅存在媒体查询或容器查询不代表适配已完成。
- 手机核心布局不得仅依赖当前目标 WebView 未生效的容器查询等特性。存在挤压、溢出、重叠、按钮不可触达或内容被遮挡时，本次前端整改不得交付为完成，必须在当前范围内修复。
- 手机样式与构建核验是普通独立前端问题的必要检查，不是业务写测试；浏览器自动化和真实手机验收仍遵守原有授权边界，未实际验证的内容如实记录，不声称已通过真机验收。

## 发布编排：自主、合批或串行

按用户最新要求，无冲突各会话自主推送；仅 Codex 冲突合批；涉及 Claude 的冲突串行排队。本节覆盖本文件及引用资料中统一合批或逐项发布的旧规则，不改变整改定位、整批授权、验证和用户验收门禁。

- 各会话在独立工作树完成本任务整改、必要核验与精确提交，按 `oa-fast-deploy` 保留就绪回执。无冲突自行正常推送、发布，不因其他会话同时开发而等待收齐或协调者；版本分配和正式激活仍持真实独占锁。
- 仅 Codex 会话实际冲突时，由唯一协调者收齐已授权且已验证的候选，线性整合为一个冻结候选，统一检查、构建、分配一个新版本并激活一次。
- Claude 与 Claude 或 Claude 与 Codex 实际冲突时，按权威队列串行发布，保留各自归属，不自动合并或 cherry-pick 对方候选。前序实际收口后刷新 dev、正式基线和队列，再核验自己的候选；不越队或派代理抢发布。从真实回执确认客户端，不凭名称猜测。
- 未完成或未授权范围不纳入发布，冻结后不插入新改动。Codex 合批才按权威合并契约保留原预留身份并登记 consolidated_into；Claude 串行排队不冒充合批。
- 用户明确要求紧急单独或隔离发布时遵从；Excel 整批仍不得拆成逐行部署。部署后仍待用户验收，不自动把表格写成完成。
- 发布门禁及生产权威以 `oa-fast-deploy` 和其 production-authority 引用为准。GitHub 禁止 full；检查绑定本次最终候选，合批不对每个原分支重复执行，无冲突直接发布不省略必要门禁。

## 先区分新增需求与原有功能整改

本节优先于下文及引用文档中的旧系统对照要求，但不改变逐图读取、权限、构建、发布和用户验收规则。

- **新增功能／独立新需求**：用户明确说明旧系统没有，或要求新增业务规则、流程、页面时，以用户完整原文、补充说明和当前新系统架构为依据。不要查询、复现或等待旧系统证据；不要为了填写模板而寻找相近旧功能、推断旧规则或要求用户提供旧截图。定位链路为“用户需求 → 当前架构与数据 → 待新增能力 → 实现与验证”。例如新建利益冲突审查流程，不要求旧系统存在对应审批规则。
- **原有功能缺陷／返工／新旧对齐**：继续按已有流程核对旧系统真实行为、源码和数据。
- 同一任务同时包含新增与整改时，分别标注，旧系统对照只适用于需要还原既有行为的部分。不得把所有单独提出的问题一律当成新增需求。
- 新需求仍须保留完整原文与逐张截图分析，明确角色权限、状态、接口、持久化、附件、触发入口和失败阻断。直接独立需求按独立问题流程实施与发布；表格批次继续遵守批次门禁。
- 定位文档的“旧系统实现”填写“不适用：新增需求，旧系统不存在”，将“新旧差异和根因”改为“需求与当前实现差距”；不伪造旧系统结论。

## P0：最高执行优先级——一行原文配一张图，定位落盘后再读下一张

这是本 Skill 内部最高优先级的执行规则。适用于首次处理、复核、返工及交接；优先于下文及引用文档中所有批量读取、整批分析和效率安排。用户最新明确指令及系统、开发者指令仍优先。

**模型每次视觉输入只能包含：当前这一行的完整问题原文＋该行完整补充/返工原文＋当前这一张实际截图。先单独分析并记录这一张，才能读取下一张；本行全部图片逐张完成并形成独立定位结论后，才能进入下一行。** 同一行有5张图，也必须执行5次独立图文输入，不能一次喂5张。

固定顺序：

1. 选定一行，结构化读全该行所有列，原文逐字保留；核对该行图片锚点、数量和顺序，运行该行 VibeHub 术语核对。图片索引只用于调度，不能代替实际看图。
2. 把该行完整原文及补充/返工原文与**仅一张**截图一起交给当前模型；同时注明工作表、行、列、图片 ID 及本行第几张。不能先全局读完文字，再脱离提示词连续看图。
3. 当前模型必须先对这张图完成分析：原文对应片段、页面/标签页/弹窗、具体字段和按钮、标注区域、新旧/返工证据角色、可确认差异、待核实事项。按需要只读追踪该图相关的新旧源码，把有证据的定位与不确定项写入本行 Markdown；不能只写“已读取”。依赖后续图片才能确认的结论标记待核实，不得提前推断。
4. 本图记录落盘后，重新携带本行完整原文，输入下一张图。新旧截图也须分别输入；对照前一张已完成的记录，必要时单张重看，不得把对照图并排一起喂入。
5. 本行所有图逐张完成后，合并本行证据、核实待定项，形成该行独立的原文—截图—源码—差异定位表，然后才处理下一行。全部行完成后才生成整批汇总；实施与发布仍遵守既有整批门禁。

禁止：跨行混喂；一次输入同一行全部截图；拼图/contact sheet 代替逐图输入；在一个 `functions.exec` 中循环 `view_image`/`image` 返回多张图；并行读取多张图后集中分析；一次工具调用接受多个图片路径；只保存路径、OCR或“已读”标记便进入下一张。工具逐次返回也不够，**两张图之间必须有本图实际分析及持久化记录**。

原表下载、原文快照、图片提取、锚点和哈希清单可以机械批量准备，但不得把它们作为批量视觉输入或定位结论。用户已一次附多张图时，先建立映射，后续重读仍一次一张。无图行独立完成原文及源码定位，不伪造截图。确需委派且已有授权时，子任务同样遵守本规则，不一次附本行全部图片。

发现违反本规则，立即停止批量看图，将受影响定位结论标记为待复核，从未合规完成的那张重新执行；不得用“同一行”“已经看过”“测试通过”豁免。

需要对照时旧系统只读，新系统可改。新增需求先应用上方任务分类，跳过不适用的旧系统环节；其余适用环节仍按顺序执行。

## 0. 整批读取与客户确认定位门禁（第一步）

处理 Excel、钉钉在线表格或其他按行记录的问题时，先完整读取用户指定批次的全部问题，再逐行定位、统一汇总确认。读取阶段可以覆盖整批所有行，但不得把多行内容混在一起分析，也不得提前修改：

钉钉在线表格必须同时读取 [钉钉在线问题排查流程](references/dingtalk-online-issue-workflow.md)。该流程规定工作表定位、完整单元格读取、浮动图片归行、未完成行识别、快照留存和输出模板；不能只查看当前屏幕可见区域。

1. 先确定本批次的明确行范围，完整读取范围内每一行。每行都从第一列扫描到最后一列，读取客户填写的全部内容，包括问题、补充说明、整改意见、返工原因、返工备注、验收备注、批注、格式、超链接和后来新增的列。
2. 提取并逐张查看本批次所有锚定截图，同时保持严格的 `图片 -> 工作表 -> 行号 -> 列 -> 表头` 映射。每张图必须归回唯一行，明确区分新系统现象、旧系统目标和返工证据；不得漏图、串行或只凭文字猜测。
   - 图片归行和“新/旧/返工”分类是两个独立判断，不能用文件名、图片出现顺序、列名或模型直觉代替视觉核对。为每张图片记录可见页面标题/菜单、业务对象、按钮或弹窗标题等**视觉身份指纹**，并记录 `映射状态=已确认/不确定`、`证据角色=新系统/旧系统/返工`。
   - 生成图片清单后做一次反向审计：逐行列出该行应有的全部图片，再逐图核对 OOXML 锚点坐标、文件清单和视觉身份指纹；发现数量不符、同一图可归多行、旧新角色无法由画面确认或列名与画面冲突时，必须停在定位阶段，补读原始工作簿/旧源码或标记待用户确认，禁止进入修改。
   - 清单至少保存 `image_id、sheet_id/name、row、col、header、filename、sha256、evidence_type、mapping_status`；无锚点、跨合并单元格或行号不确定时填 `mapping_status=不确定`，不能靠相邻行、文件顺序或截图内容猜回去。
   - 有 JSON manifest 时，在用户定位确认前运行 `scripts/validate-screenshot-manifest.py <manifest> --require-old-new`；对实际提供返工截图的行另取该行 manifest 运行 `--require-rework`，不得对混有无返工图行的整批 manifest 加此参数，并把校验结果路径写入批次汇总。只有返工文字、没有返工截图的行，完整保存原文及旧新源码/数据证据，不伪造或额外索取截图；真实校验失败须修正证据后再进入实施。同一单元格允许多图，保留各图独立image_id、真实锚点与visual_identity，不得篡改列号规避判重。原表仅提供一侧截图时，可按[源码补证格式](references/screenshot-source-evidence.md)登记已逐项核对的对应源码，以 `--source-evidence <json>` 补足old/new证据；不必要求用户为校验脚本额外提供截图。源码补证不能替代已有截图的逐图查看，不能替代真实返工截图，也不代表已完成浏览器验收。
3. 按行独立完成定位。对每一行分别执行 VibeHub 术语辅助、旧系统页面/源码/数据链路、新系统页面/API/模型/权限/状态链路和历史整改记录追踪；禁止用一行的结论套用其他行。
4. 为每一行形成独立定位确认单，逐项写清：客户原文、全部截图观察、旧系统真实行为、新系统实际偏差、根因、影响范围、拟修改文件与完整整改方案、验收动作和风险。定位粒度必须具体到页面、数据、功能和按钮：写明菜单路径/页面标题/标签页或弹窗区域；列表或详情使用的数据实体、关联字段、筛选范围、权限范围和状态；用户从入口到结果的完整操作流程；每个按钮的名称、位置、可见条件、可用条件、点击结果、校验、持久化和后续流转。禁止只写模块名称、笼统现象或“功能不对”。
5. 全部行定位完成后，生成一份整批问题定位汇总。汇总必须列出每一行的模块、现象、根因、修改范围、共享影响和依赖/冲突，并明确哪些问题可共用修复、哪些必须独立处理。
6. 把全部逐行定位确认单和整批汇总一次性交给用户确认并停止。只有用户明确认可整批定位后，才允许编辑代码、创建测试数据、运行写操作、提交或部署；不得以“某一行已经定位清楚”为由提前开始局部修改。
7. 用户要求调整定位时，补充受影响行的证据并重新生成整批汇总；不得把用户的纠正直接当作修改授权。
8. 获得整批定位确认后才进入实施阶段。按照确认后的完整问题清单一次性完成整批代码改动；不得每改一行就暂停确认、测试、提交或部署。所有改动完成后统一执行回归测试、生产构建、证据登记、提交和一次部署。

### 多行与单问题等质门禁

在线表格包含多行时，只有原始快照、图片提取、索引/哈希等机械准备可批量执行；模型图文输入与定位严格按开头 P0 一行一图顺序执行。实施阶段的测试调度可批量进行。每一行在进入整批修改前，都必须达到“用户单独发送该行 Excel 原文和截图时可直接实施”的质量：

1. 该行原文、补充、返工文字和全部图片已完整归档，图片与行/列唯一对应；不能只保留整批摘要。
2. 每张图片都已逐图记录页面、业务对象、可见数据、功能入口、按钮和标注区域；不能用 OCR 摘要或另一行截图代替。
3. 旧系统目标和新系统现状均已追踪到真实入口、前端、后端和数据库。若某层不涉及，必须写明依据；若证据不足，必须标记未知，不能猜测后直接修改。
4. 必须检查用户真实入口矩阵和生产数据假设，例如同一状态可由哪些页面/API 写入、人员/部门/权限/历史记录在线上是否真实存在。只测试内部函数或理想夹具不算完成。
5. 该行具有独立的根因、修改落点、原子验收项、聚焦测试、失败路径、持久化和清理方案。任一行未达标，整批不得进入实施。

全部行达到等质门禁后，生成“共享改动矩阵”，按组件、接口、服务、表和业务入口合并实现：同一根因只修一次，但每一行仍保留独立验收映射。可以并行修改互不重叠的文件或领域；共享文件由一个明确所有者统一编辑，禁止多个任务分别覆盖。整批完成后一次性执行逐行聚焦测试、共享入口矩阵测试、跨行交叉回归、生产构建和数据清理，再统一提交和发布。

### 主动问题发现模式

当用户要求“学习这类问题、自己找问题并解决”，而没有指定新的 Excel 行或要求先停在定位确认时，进入主动问题发现模式：把历史问题表、返工文字、截图和旧系统实现当作缺陷模式样本，主动扫描新系统中相同的页面入口、按钮事件、请求参数、权限/数据范围、状态流转、分页、附件和多条数据录入链路。每个候选问题仍必须完成“用户原文/截图证据 -> 旧系统行为 -> 新系统链路 -> 根因 -> 修改点”的证据闭环；确认存在确定性偏差后，可在当前批次内一次性实施修复，不得为了等待用户逐条引导而停工。主动发现的修复必须保留原始问题文字，不得把模型推断写成用户原话；没有足够旧系统或业务证据的问题记录为待核实，不得猜测性改动。主动模式默认只做本地修改、测试和构建，部署仍以用户当前指令为准。

#### 从用户缺陷样本反向发现未提问题

在线表格中的问题是用户已经发现的样本，不是系统缺陷的完整范围。处理表格时，必须把每条已确认问题抽象成“缺陷模式”，再对旧系统和新系统中同一业务域的同类入口做横向扫描，主动找出用户尚未填写但同样没有对齐的地方。至少覆盖以下同类维度：

1. 菜单可见性与入口路由、页面/标签页/弹窗载体、字段名称顺序和默认值。
2. 按钮出现条件、可用条件、请求参数、前端校验、后端校验、失败提示和成功后的刷新。
3. 角色权限、人员与部门绑定、数据范围、历史数据兼容及越权阻断。
4. 列表筛选、分页上限、总数统计、排序、固定列、滚动区域和详情跳转。
5. 单条与多条数据录入、状态流转、审批/任务/通知/日志、附件上传下载预览和文书生成。
6. 旧系统同一入口的控制器、服务、数据表、关联字段与下游结果是否在新系统形成完整闭环。

主动扫描必须按“样本 -> 缺陷模式 -> 同类入口清单 -> 旧系统证据 -> 新系统证据 -> 差异候选 -> 根因确认”的顺序执行，不能只修用户指出的那一页。扫描结果分为“已确认不一致”“已核对一致”“证据不足待核实”三类；只有前一类才能进入整改，后一类不得凭推测修改。每个主动发现的问题都要有独立记录，标明来源样本、受影响页面/按钮/API/数据关系、证据、修改点和验收动作；不能把主动推断写成用户原始问题。若当前是在线表格批次，主动发现的问题必须追加到同一批定位汇总，仍遵守整批定位确认后一次性修改；若用户明确要求直接解决，则按确认的主动发现清单统一实施，而不是逐个临时修补。

- 自动化测试、构建、持久化/API 验证、失败路径、清理和用户验收清单。

代码修改必须能够逐项回指该 Markdown 的修改清单；禁止先改代码后补写一份泛化说明。

创建整改文档时必须读取并使用 [整改 Markdown 标准模板与示例](references/remediation-markdown-template.md)。模板中的必填章节不得删除；不涉及的前端、后端或数据库层必须填写“不涉及”及依据，不能留空。示例只说明填写粒度，不得复制示例中的虚构业务结论到真实问题。

### 定位输出最小粒度

每个问题的定位结论必须同时包含以下四组信息，缺少任一组均视为定位过粗，不得交给用户确认或进入整改：

- **具体页面**：一级菜单、二级菜单、页面标题、业务对象、标签页/详情区/弹窗或抽屉名称，以及截图中的准确区域。
- **具体数据**：页面读取和写入的业务实体、主关联键/软关联字段、状态字段、筛选条件、人员与部门权限范围、历史数据兼容和上下游记录。
- **具体功能**：入口、前置条件、操作步骤、成功结果、失败提示、状态流转、刷新后持久化结果，以及对列表/详情/审批/任务/通知/附件等下游的影响。
- **具体按钮**：截图和旧系统中出现的每个按钮或菜单项，逐个记录名称、位置、展示条件、禁用条件、点击载体、字段默认值、提交接口和结果；新系统缺失、多余、错位或行为不一致的按钮必须分别列出。

截图较多时仍需逐图逐区域登记，不得用一张图的观察替代同一行其他截图，也不得把多个按钮概括为“相关操作”。

旧系统截图只是线索，不是完整规格。涉及多步骤时必须结合旧源码和数据还原全部步骤；涉及 UI 等价时逐项比较：页面载体、标题、步骤、区块层级、字段名称和顺序、输入类型、默认值、可编辑状态、按钮、校验、持久化和下游结果。旧系统是整页流程时，不能用弹窗或抽屉冒充等价实现。

缺少任一层记录时仍属于粗略定位，禁止修改代码。

逐层定位完成后，必须先执行第 0 节的客户确认定位门禁；不得从定位结论直接跳到完整整改。

## 5. 返工问题

返工前先做误判审计，不得直接叠加补丁：

1. 逐字重读原问题、原整改意见、全部返工文字和截图。
2. 使用原始截图、旧源码、控制器和旧库数据还原原角色和入口。原记录不存在时使用同角色、同模块、同状态的等价数据并记录替代依据；只有用户明确要求时才控制浏览器重跑。
3. 对照旧源码、数据和上次代码差异，指出上次遗漏的具体场景、层级或路径。
4. 核对上次验证的角色、记录、前端构建、API、数据库和线上活动版本，判断是否使用了错误页面、数据或运行实例。
5. 记录误判归因：需求读取、旧系统复现、实现范围、测试数据、浏览器验收、运行实例、部署或台账。

返工审计还必须优先排查：截图映射错误、证据类型误判、把相邻行/相邻页面当成目标、把截图顺序当成流程顺序；先复核 manifest、图片哈希和页面结构指纹，再审计历史提交，不能直接叠加补丁。

审计未完成前禁止重新修改、部署或标记 `1`。

### 真实入口与生产数据假设门禁

返工审计和自动化验证必须覆盖用户实际操作路径及线上真实前置条件，禁止用理想化夹具掩盖生产缺口：

1. 记录用户实际使用的菜单、页面、按钮、保存入口、对应 API 和最终下游实体。测试必须经过同一条业务调用链；只测相邻接口、公共函数、源码正则或调用次数不能证明问题已修复。
2. 代码涉及固定人员、部门、角色、状态、参数、模板或其他主数据时，修改前必须只读核对权威线上数据，记录匹配数量、唯一性和启用状态。缺失、停用、重名或历史脏数据必须有明确处理；禁止静默跳过。
3. 测试夹具必须包含线上已观察到的真实前置条件。可以测试理想路径，但必须同时覆盖目标数据缺失、停用、重复、权限不足和历史记录等失败路径；不得虚构线上不存在的人员或配置，并把该夹具作为唯一通过证据。
4. 自动触发、任务或提醒类问题必须建立触发矩阵，至少覆盖：每个用户入口、字段与状态变更的不同先后顺序、定时补偿/历史回填、重复执行幂等、目标人员缺失、持久化、通知/日志和下游列表可见性。
5. 用户反馈同一批次任一已发布功能未生效时，除复查当前症状外，还必须重新审计该批次所有共享触发逻辑和相邻行；在逐行回放完成前不得继续宣称整批已修复。
6. 当线上真实数据无法满足旧系统目标时，不得猜测、静默失败或通过造数绕过。必须记录数据缺口，并采用需求已有依据支持的降级规则；没有依据时先向用户确认。

完成报告必须列出“实际入口覆盖矩阵”和“线上数据假设核对”。缺少任一项，返工状态仍为未完成。

## 6. 完整整改

对于 Excel/钉钉表格批次，仅当指定范围内全部问题都已完成定位、形成整批汇总并通过第 0 节的用户确认门禁，才允许进入本节；不得按单行确认结果提前修改。

只修改新系统，并保留其他任务和用户的无关改动。根据根因覆盖所有必要层：

- 页面布局、字段、链接、交互和错误提示；
- 前端状态与真实 API；
- 后端校验、权限、角色范围和状态机；
- 数据库字段、关系、迁移和历史兼容；
- 审批、任务、提醒、日志、通知、附件、审计和下游可见性。

禁止空壳实现、生产硬编码、虚构人员、前端假成功或固定响应。后端事务成功后才能提示成功，刷新后必须仍成立；失败时不得残留部分写入。共享逻辑有缺陷时检查所有同类入口、列表、详情和角色，不只修截图页面。

为根因添加聚焦回归测试，并运行受影响的前后端测试和生产构建。前端只能在本地构建；服务器不得运行 `npm run build`、Vite 或 TypeScript 编译。

## 7. 本地自动化验证

默认不打开或控制任何浏览器；页面业务测试由用户完成。只有用户对当前问题明确要求浏览器自动化时，才允许使用 Google Chrome 插件/backend；永久禁止 Codex 内置 Browser Use (`iab`)。

1. 运行根因对应的前后端聚焦测试和相邻回归测试。
2. 对 API、权限、状态机、事务、数据库关系、历史数据兼容和失败原子性进行可重复验证。
3. 涉及持久化时验证写入、重新读取和下游实体；涉及附件时验证实体数量、元数据、物理文件和权限接口。
4. 运行生产构建并确认产物来自当前工作树。
5. 保存测试命令、结果、构建结果、数据前后计数和清理结果。

### 业务结果一致性放行闸门（Excel/在线表格批次）

每行在报告“本地整改完成”前，由主任务独立复核原问题、补充和最新返工文字，建立逐项验收映射：`原文片段 -> 适用角色/真实入口/权威数据来源 -> 实际代码差异 -> 应出现及不应出现的结果 -> 自动化验证及回读证据路径或待用户页面验收 -> 通过/失败/未验证`。旧系统截图、源码和数据只用于确定规则；源码存在、单元测试通过、构建成功或页面能打开，均不能替代可自动验证的业务结果证据。任一可自动验证的原文片段缺少结果证据、测试未覆盖用户实际入口，或结论为失败/未验证时，该行保持未完成，整批不得发布；纯视觉呈现列明验收动作并保持 `待用户验收`，不得声称已通过页面测试。

按问题实际涉及的维度验证，不机械增加无关测试：

1. **条件与例外**：把应纳入、应排除和边界状态分别列出，使用同一业务对象证明允许与阻止两侧行为；例如归档资格不能只测一种费用或只测全部已结清。
2. **数据来源与归属**：追到记录的创建入口、上传者/所属账号、关联对象、筛选条件和去重键。对归集或同步类功能，分别验证应进入与不应进入的记录，并在目标列表、详情及持久化数据中核对；不能只按文件名、关键词或截图外观推定来源。
3. **权限与计数**：写明纳入/排除条件、状态和时间窗口；在同一角色、同一账号、同一筛选条件下，对照徽标/汇总数、列表总数、可见详情和点击目标的实际记录，再用不同账号验证隔离。计数与列表不一致时，不得把其中一侧单独通过当作整项通过。
4. **异步与关系闭环**：定时功能核对调度配置、实际执行记录及执行前后数据；新增、删除、解绑或同步功能核对正向与反向关联、刷新回读和下游可见性。仅有配置、按钮或成功提示不算完成。

发布前重新读取线上指定行的全部已用列及图片锚点，与定位时快照逐项比较。原文、返工、图片或状态有新增或变化时，先使受影响行的旧验收映射和“已完成”结论失效，补齐定位与验证后再进入整批放行；不得用旧报告覆盖最新反馈。无法自动验证的页面呈现仍标 `待用户验收`，不得声称已通过线上业务验收。

自动化失败立即回到定位和整改。自动化通过只表示 `待用户验收`，不能写 `1/已验收`。

本节只适用于 Excel 行或用户明确要求测试的直接问题。普通直接问题按第 1 节实施并选择自主、合批或串行发布，不运行本节测试。

## 8. 清理与完成状态

只清理本任务创建的测试记录及其工作流、通知、附件、任务、提醒、日志和审计；不得清理真实业务或旧系统数据。必要时恢复被测试修改的计数和时间。

`1` 只表示用户已经按原始文字、全部截图和返工要求完成页面测试并明确确认通过。代码、接口、构建、部署或自动化测试都不能单独推导 `1`；未收到用户确认时保持 `待用户验收`。

## 9. 发布与线上验收

每次发布显式读取并遵守当前安装的 `oa-fast-deploy` 及其 `production-authority` 引用，以实际生产配置和队列为准。

- 独立问题：整改完成后保留就绪回执；无冲突各自直接推送、发布，仅 Codex 冲突合批，涉及 Claude 的冲突串行排队。不运行本地或线上业务测试，不等待第二次发布授权。
- Excel 批次：全部行本地闭环后统一发布一次。
- 保持 `dev` 线性，由本次实际发布所有者整合自己的授权就绪范围；Codex 合批才由唯一协调者整合各候选。普通发布不得制造 merge commit、force-push、覆盖目录或夹带无关改动。真实历史分叉须另获明确的历史重写授权和修复方案，普通合批或协调发布授权不包含强推；修复前保存安全引用并完整保留两侧有效改动。
- 正式版本按发布队列连续分配；失败或回滚版本仍占用。
- 按实际 enterprise immutable package/current 链路安装新包并激活一次，使用权威发布队列及发布 mutex；不部署覆盖旧工作树，不修改旧包。
- 无数据库变更无需 dump；有迁移或数据补丁时，仅备份受影响表及必要关联行到批准的外部位置并校验 SHA256，服务器不保留备份。结构使用幂等迁移，业务数据按明确清单处理，禁止整体覆盖线上库。
- 上传本地验证过的前端产物；服务器只做校验、迁移、切换、重启、健康检查和回滚。
- Windows 到 Linux 的复杂操作写成独立已审脚本后上传执行，不在 PowerShell SSH 字符串中嵌套管道、变量或 JSON。

部署后只核对提交、标签、包版本、静态资源、实际 systemd/current 配置、API/Web 健康和严重错误日志，不执行服务器业务测试，也不主动打开 Chrome；记录 `待用户验收`，等待用户在实际已发布入口测试并反馈，不把退役测试端口当作固定目标。

用户反馈线上失败时保留反馈和截图并标记返工；按风险决定回滚或修复前进，后续使用新版本号。用户明确反馈通过后更新验收状态；Excel 行再按原表定义写入 `1`。

用户明确要求暂停提交、推送、发布、服务切换或线上写入时，立即停止对应动作。

## 10. 最终报告

报告必须包含：问题/行号、具体根因、完整改动范围、自动化测试和构建、测试数据清理、发布版本/提交、数据库迁移或数据补丁、服务/API 健康、用户验收状态和回滚点。未收到用户确认时明确写 `待用户验收`，不能声称已验收。
