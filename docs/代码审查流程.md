# 代码审查流程（第一阶段：只报告，不拦截）

陶威 2026-11-07 同意，先试运行 2 周。现有门禁（`scripts/quality_gate.py`、CI、pre-push）防的是改坏；这套流程防的是代码越堆越乱，并让风险高的改动多过几道人和测试。

- 第一阶段任何报告结果都不让推送、CI 或发布失败。门禁本身的规则和结果不变。
- 沪知全员上线稳定后才讨论要不要拦截，由陶威决定。
- 不大重构，老问题不要求一次修完。

## 按风险分三档

每次推送自动判档（`scripts/review/risk.py`），只能往高提，不能往低降。

| 档位 | 自动判定 | 必须做 |
| --- | --- | --- |
| 低 | 只改文档、测试、样式、图片 | 开发 + 工具层 |
| 中 | 其他业务代码 | 工具层 + 独立审查 + 相关测试 |
| 高 | 权限、财务、数据写入、数据库结构、同步、发布和质量门（CI、门禁、依赖、部署、基线）；或者改动行里有写库语句 | 验收场景 + 独立测试 + 前后接口对比 + 独立审查 + 人工拍板 |

人工拍板：技术和数据问陶威，业务规则问陶国南。

判档的局限：

- 财务和数据写入散在各处，主要按文件名判（含 fee、invoice、payment、incoming、`_delete`、`_merge` 等），文件名看不出来的判不到。
- 写库语句抓直接 SQL 和 ORM 的新增、删除、批量写；改已查出对象的字段（`record.status = ...`）是普通赋值，抓不到。这种情况靠派活时人工提档。
- 改名时新旧路径都判。

调度提档有两种方式：在派活说明里写明“按高风险”，开发会话在提交说明加一行 `Review-Tier: high`；或者跑报告时加 `--raise-to high`。

### 高风险各环节要交什么

| 环节 | 谁做 | 产物 |
| --- | --- | --- |
| 验收场景 | 开发前写，业务规则以单子和拍板人为准 | 单子里写明：谁、在哪、做什么、应该看到什么，含失败和无权限的情况 |
| 独立测试 | 不是写代码的会话 | 按验收场景跑的结果，失败项原样贴 |
| 前后接口对比 | 独立测试的会话 | 同一身份、同一请求，改动前后返回的差异，说明每处差异是不是预期 |
| 独立审查 | 新会话 | 见下 |
| 人工拍板 | 陶威或陶国南 | 钉钉或问题处理中心里的明确答复，经调度转回 |

中风险的“相关测试”指覆盖这次改动行为的测试；报告列出的没覆盖的改动行要么补测试，要么在单子里说明为什么不补。

## 独立审查怎么做

- **写代码的会话不能给自己过审。**
- 独立审查开新会话，只看单子和改动（`git diff`），不看开发过程，不接收开发会话的结论，免得被带偏。
- 看四件事：改动是否满足单子；有没有改坏相邻功能；有没有先找现有实现（重复造轮子）；被替代的旧代码清了没有。
- 结论写成“通过”或“退回”，退回必须列具体问题（文件、行、会出什么错）。

## 交接和退回

- 代理之间靠单子和产物交接：单子、提交、审查报告、测试结果。不靠口头转述，也不靠某个会话的记忆。
- 同一问题最多退回 2 次，再不过就报调度，由调度决定换人、拆单或问陶威、陶国南。
- 派活要求：先找现有实现再写；改完清掉被替代的旧代码；上线前不大重构。

## 工具层

报告脚本 `scripts/review/report.py`。门禁通过后 pre-push 自动跑一次，最多 3 分钟，到点杀掉子进程并放行。Git 在钩子前就连上了远端，空闲约 6 分钟可能被 GitHub 断开（分支 2 测过一次），所以门禁加报告不超过 5 分钟：门禁用时长就相应缩短报告的时限，剩不到 20 秒就跳过；发布时 `dev`、`main` 推同一提交，第二次复用报告不重跑。工具崩溃或超时记入报告开头的“本次不完整”，不会写成没问题。

这些脚本的测试在 `tests/review/`，只由 CI 的报告工作流跑，不进门禁：报告或基线坏了不能挡推送。

CI 由 `.github/workflows/review-report.yml` 在推送和每晚跑（发布提交带 `[skip ci]`，推送时大多不触发，所以靠每晚那次）。

| 检查 | 工具 | 是否新增依赖 | 说明 |
| --- | --- | --- | --- |
| Python 规则扩大 | Ruff，配置 `scripts/review/ruff.toml` | 否 | 门禁仍读 `pyproject.toml` 的 `select = ["F"]` |
| Python 类型 | mypy | 是 | Ruff 不做类型推断 |
| 复杂度 | Ruff C901、PLR0915；前端 `ts_metrics.mjs` | 否 | 超过 15 算复杂；前端函数超过 200 行算过长 |
| 重复代码 | `report.py` 自带 | 否 | 连续 12 行相同才算。改了变量名的抓不到 |
| 无用代码 | vulture；前端 `tsc` 和 `ts_metrics.mjs` | 是（vulture） | 不看 ORM、Pydantic 字段，误报太多 |
| 依赖漏洞 | pip-audit、npm audit | 否 | 要联网，依赖文件有改动时或 CI 才跑 |
| 改动行覆盖 | coverage.py | 是 | 见下 |
| 前端类型 | tsc | 否 | 项目已有 |

三个新增依赖都带哈希锁在 `requirements-review.lock`，装在独立环境（`sh scripts/install-review-tools.sh`），不进门禁的 Python 环境，因为门禁会校验自己的环境没变化。没装也能推送，报告会写明少了哪几项。

### 覆盖率的范围

- 推送时：只跑提到改动模块的相关测试，最多 8 个文件，这次改到的测试优先。数字偏保守：没跑到不等于别的测试也没覆盖。
- 测试环境：去掉密钥类环境变量和 Git 环境变量，不跑 probe 脚本；跑完工作区多了文件会在报告里提示。
- CI：跑全部后端测试，但没有 PostgreSQL，依赖 PostgreSQL 的测试不计入。
- 前端不算行覆盖：前端测试大多读源码文本断言，不执行页面代码，算出来的数字没有意义。报告改为列出没被任何前端测试提到的改动文件。

### 基线

- 老问题记在 `scripts/review/baseline.json`，只比新增。比较时读比较基准提交里的基线，所以同一次提交加问题又刷基线，问题照样报出来；改基线判高风险，报告开头会标出。
- 问题按“文件 + 规则 + 这一行的内容”比较，不用行号，所以代码上下挪动不算新问题；这一行内容改了，老问题会被算成新问题，这是有意的，改到的地方顺手看一眼。
- 报告分三类：改动行上的新增（主要看这个）；改动文件其他位置的（函数变复杂会落在这里）；基线之后别处累计的（看整体有没有变乱）。
- 刷新基线：`python scripts/review/report.py --update-baseline --audit`，有工具没跑成时不会写入。试运行期间不刷新，累计数才有参考价值；结束时再决定。

### 报告看哪里

- 推送时控制台一行摘要，含报告路径。
- 完整报告：Git 目录的 `oa-review/<提交前 12 位>/report.md`，所有 worktree 共用。
- CI：运行页的 Summary 和 `review-report` 产物。
- 自动统计：`python scripts/review/report.py --trial-summary`。
