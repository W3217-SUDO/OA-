## 3. 旧系统实现
已反编译GD.CRM.WEB/bin/Dchien.Legal.DataAccess.dll的CaseSearchDao，证据.codex-evidence/roi/CaseSearchDao.cs:1040,1345明确Tuple3官费亏损、4已付官费、5已收非官费、6平均周期。旧JS按`((非官费回款*0.15-官费亏损)/已付官费/平均周期)*365*100`，官费支出为0时100。
只读SQL Server OBJECT_DEFINITION(V_Legal_Case_Fee)确认：已付官费来自有效已支付AP付款对象；官费回款来自有效AR付款对象；亏损只在106018阶段为支出减回款；非官费限11020010律师代理费、20律师咨询费、30律师培训费、40律师见证费；通知日MIN(CaseFee.InformDate)，回款分配日MIN(AR付款对象.CreateTime)。Rate/Cycle需有回款分配日期；品牌另排除106018。DAO按各组财务值与日期distinct后整数平均天数。Deficit图不要求回款日期。

## 4. 新系统当前实现
### 前端
ReportCenterPage通过reports/analytics取图值，只绘数值；资金回报率无不可计算原因。
### 后端
core/system.py::_report_analytics把所有费用amount当支出，paid_amount当回款，received/expense比值，无财务类型、周期或归档阶段口径。
### 数据库
BusinessRecord(finance/case)、FinanceTransaction(真实付款)、IncomingPayment.allocations(真实回款分配，含allocated_at与settlement_items)。费用data含fee_type_code、fee_type、inform_date及既有汇总。仅查询；不迁移、不补旧缺失分配日期。

## 5. 新旧差异和根因
旧Tuple字段曾被省略为泛化收支比例。现在按真实来源建立每案官费支出/回款、指定非官费回款、最早通知及回款分配日期，再按客户/律师汇总。不能将付款当回款、申请金额当已支付，不能把银行到账日期冒充分配对象创建日。

## 6. 精确修改清单
- [x] 新core/roi.py：以权限内案件和费用建立聚合；使用真实付款流水和明确fee关联回款分配，已持久化金额快照仅无明细时兼容读取，不与明细重复相加；无分配日期不伪造。
- [x] core/system.py：品牌/律师图接入新聚合，退款/执行分支保留由其他修复负责。
- [x] ReportCenterPage.tsx：主任务已批准，显示不可计算原因；数值不可计算不填0。
- 无数据库层变更。金额权限缺失时不读金额；保留现有记录权限。影响同一四张资金运营图和导出。
- 旧SQL的未指定顺序top30不稳定，当前按组名称稳定排序后最多30；不会重建旧硬编码客户/员工名单。
