# 逐动作交替对照验收规则

## 当前目标

以申浩旧系统为业务基准，在本地 `dev` 分支完成 OA 全站功能对齐。申浩旧系统允许创建带统一测试前缀的数据并对这些自建数据完成真实业务闭环，但严禁修改任何已有数据。主会话只负责项目管理、任务拆分、监督、验收和串行 Git 提交；独立开发任务负责双站对照、实现、测试和数据清理。全部功能在本地验收完成后，才统一部署测试服务器。

## 强制执行顺序

每个菜单、页面、按钮、字段、弹窗、跳转、筛选、分页、上传下载、导入导出、权限拦截、状态流转、审批和失败路径都必须按以下顺序执行：

1. 在申浩旧系统打开目标页面并执行一个动作；需要写入时，只能操作本任务创建的测试数据。
2. 立即切换到本地系统，在对应页面执行同一个动作。
3. 逐项比较出现条件、字段、按钮、弹窗、跳转目标、提示、权限、状态变化和后续关联页面。
4. 发现本地缺失或行为不同，立即在本地完成最小修复、定向测试，并重新操作两个系统复验。
5. 当前动作一致后，才能回到旧系统执行下一个动作。

禁止先完整盘点旧系统、再单独检查本地系统；禁止只看菜单、截图、源码或测试用例后宣称对齐。

## 旧系统数据边界

- 旧系统允许创建以 `CODEX-*` 开头的测试数据，并对本任务创建的数据执行编辑、保存、审批、上传、下载、状态流转和删除。
- 旧系统严禁修改、审批、删除、覆盖或关联破坏任何已有数据；无法确认归属的数据一律视为已有数据，不得写入。
- 本地系统同样使用 `CODEX-*` 前缀测试数据完成真实成功与失败闭环。
- 两个系统都只能删除本任务创建的测试数据、附件和临时文件，不得删除其他任务或用户的任何数据。
- 每个测试对象在创建时记录系统、前缀、业务编号和关联对象；闭环结束后逐项回查，证明两边均零残留。

## 每个动作的验收证据

每一步必须成对记录：

- 申浩旧系统的实际 URL、页面名称、执行动作和结果。
- 本地系统的实际 URL、页面名称、同一动作和结果。
- 两边的明确差异；若无差异，也要说明实际核对了什么。
- 修复文件、定向测试和修复后的双站复验结果。
- 两个系统的测试数据、数据库记录、附件和临时文件的精确清理结果。

缺少任一侧实际点击证据，或旧站停留在无关页面/iframe，均不得通过验收。

## 跨模块付款跳转

合同、案件、费用、报销、票据或其他来源页面跳转到付款模块时，必须同时验证来源端和付款端，不能只证明目标页面能够打开：

- 跳转必须携带并定位正确的来源记录、业务编号、客户、金额、合同或案件关联，不得落到未筛选的普通列表首页。
- 付款申请、审批、待付款、付款、核销、驳回和撤回后的状态及金额必须同步回来源页面和关联列表。
- 必须验证返回路径、无权限拦截、重复申请阻断、已占用金额阻断、目标不存在和接口失败提示。
- 来源模块任务与财务模块任务使用同一组 `CODEX-*` 业务编号交叉复验；双方证据齐全后才能通过。
- 两个系统各自完成创建、跳转、状态流转、回写和精确清理，且不得操作已有付款或来源记录。

## 提交与部署

- 所有修改仅进入 `dev` 分支。
- 每个最小业务闭环完成后，由主会话复核差异、测试、构建和清理，再按明确文件串行 Git 提交。
- 本地全站验收完成前不部署；全部完成后统一部署测试服务器并再次验收。
