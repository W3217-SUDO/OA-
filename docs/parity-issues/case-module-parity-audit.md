## 一、列表结构对比

### 旧系统（按 PageId 分独立页面）

| PageId | 页面含义 | 数据范围 | 阶段过滤 |
|--------|---------|---------|---------|
| 1001104030 | 待开庭案件 | 我的（UserId=当前用户） | 101015(一审开庭) / 102013(二审开庭) / 103012(再审开庭) |
| 1001104040 | 待结案案件 | 我的（UserId=当前用户） | 101022(一审结案) / 102022(二审结案) |
| 1001104050 | 等待上诉案件 | 我的（UserId=当前用户） | 101019(一审判决) |

此外还有：
- **排期列表**（ScheduleList）：按开庭日期排序，从今天开始
- **阶段列表**（PhaseList）：按阶段分组统计
- **执行列表**（ExecutionList）：PageId 1001101200 / 1001103200

### 新系统（统一列表 + scope + 状态过滤）

新系统案件搜索接口 `POST /cases/search` 使用 `scope` 参数区分数据范围：
- `mine`：我的案件（owner + 协作人 + 旧参与人迁移）
- `department`：部门案件
- `company`：公司案件

案件状态通过 `case_statuses` 过滤，前端通过左侧阶段树进行过滤。

### 差异分析

1. **列表组织方式不同**：旧系统按阶段拆成独立页面，新系统是统一列表+状态过滤。这是 UI 设计差异，不影响业务逻辑。
2. **数据范围体系不同**：
   - 旧系统案件列表默认是"我的"，通过 AccessLevel 判断是否有更高权限
   - 新系统明确区分 mine/department/company 三级，与客户模块的范围体系一致
   - **待核实**：旧系统管理员/经理能否看到部门或全所案件列表？

## 二、案件删除对比

### 旧系统（CaseService.DeleteCase + CaseDao.DeleteCase）

```csharp
// CaseDao.DeleteCase — 逻辑删除
UPDATE dbo.Legal_Case
SET IsActived = 'F', ChangeUser = @ChangeUser, ChangeTime = @ChangeTime
WHERE CaseNo = @CaseNo
```

关键特征：
- **逻辑删除**：只更新 `IsActived = 'F'`，数据保留在表中
- **无事务包裹**：直接 foreach 循环，逐个删除，失败不回滚
- **无级联删除**：不删除关联的案件文件、费用、事件、日志等
- **写案件日志**：每条删除写入 `Legal_Case_Log`，内容为"案件已删除"
- **无权限校验**：服务层没有权限检查（权限在 Controller 层？）
- **无归档/合并状态校验**：没有检查案件是否已归档或已合并

### 新系统（_delete_company_cases）

关键特征：
- **物理删除**：`db.delete(record)` 直接从 `business_records` 表删除
- **级联删除**：删除关联的任务、附件、协办费、开庭排期、财务流水、工作流事件
- **事务保护**：整批在一个事务中，失败全回滚（"整批未删除"）
- **权限校验**：仅 admin 和 manager 可删除
- **状态校验**：已归档、已合并案件禁止删除
- **加锁预检**：`with_for_update()` 先锁定整批再删除
- **附件清理**：提交后清理不再被引用的物理文件

### ⚠️ 重要差异：逻辑删除 vs 物理删除

| 维度 | 旧系统 | 新系统 | 风险 |
|------|-------|-------|------|
| 删除方式 | 逻辑删除（IsActived='F'） | 物理删除（DELETE FROM） | 中：旧系统保留数据但无恢复入口 |
| 关联数据 | 不删除，保留 | 级联删除任务/附件/费用等 | 中：旧系统可恢复关联数据 |
| 事务 | 无，逐个执行 | 有，整批原子 | 新系统更安全 |
| 权限校验 | 服务层无 | 服务层有（admin/manager） | 待查旧系统 Controller 层 |
| 归档检查 | 服务层无 | 有（已归档/已合并禁止删除） | 待查旧系统前端是否限制 |
| 回收站/恢复 | **无**：没有案件回收站，没有恢复功能 | **无**：物理删除不可恢复 | 功能一致，均不可恢复 |

**补充发现（已核实）**：
- 旧系统所有案件查询默认过滤 `IsActived='T'`，已删除案件不出现在任何正常列表中
- 旧系统**没有案件回收站页面**，也没有恢复删除案件的功能（与客户模块不同）
- 案件合并时，目标案件走同一套 DeleteCase（IsActived='F'）逻辑
- 删除按钮出现在多个列表：执行列表、排期列表、归档列表（已归档也能删？）、各类型案件列表

**结论**：
虽然删除方式不同（逻辑删除 vs 物理删除），但**从用户视角看效果一致**——删除后案件消失，且都无法恢复。旧系统的逻辑删除只是"数据保留策略"，不是面向用户的功能。

但仍有以下差异需要业务确认：
1. 旧系统已归档案件也能删除（归档列表页有删除按钮），新系统禁止删除已归档案件——哪个正确？
2. 数据保留合规性：法律行业是否要求保留已删除案件的痕迹用于审计？

## 三、案件分配对比

### 旧系统（UpdateMultipleCase 方法）

```csharp
public bool UpdateMultipleCase(List<string> caseNos, List<string> courtLawyers,
    List<string> caseLawyers, List<string> caseAssistants, List<string> businessOwners,
    int? casePhaseId, decimal? litigationAmount)
```

- 批量修改：开庭律师、经办律师、律师助理、业务负责人、阶段、诉讼金额
- 已归档案件不允许修改基本信息（抛 ApplicationException）
- 人员变更时会发消息通知
- 同步更新 CaseParticipant（参与人表）
- 阶段变更时自动写入对应时间（分案日期、立案时间、结案时间等）
- 每条变更写案件日志

### 新系统（assign_case 接口）

```
POST /cases/{case_id}/assign
```

- 单条分配：开庭律师、经办律师、律师助理、客户管理人
- "新案待分配"状态自动流转到"文书准备"
- 自动生成文书准备任务
- 自动生成时间戳证据交接任务
- 如果有公证，自动生成公证原件交接任务
- 写工作流事件（WorkflowEvent）

### 差异分析

| 维度 | 旧系统 | 新系统 |
|------|-------|-------|
| 操作方式 | 批量修改多字段 | 单条分配 |
| 可分配人员 | 开庭律师、经办律师、助理、业务负责人 | 开庭律师、经办律师、助理、客户管理人 |
| 状态流转 | 可直接修改阶段（casePhaseId） | "新案待分配"→"文书准备" |
| 自动任务 | 无 | 文书准备任务、证据交接任务、公证交接任务 |
| 归档校验 | 有（已归档禁止修改） | 待查 |
| 通知 | 系统消息+短信 | 工作流事件 + 任务通知 |

**待确认**：新系统是否有批量分配功能？旧系统的 `UpdateMultipleCase` 是独立功能还是列表上的批量操作？

## 五、案件参与人机制对比

### 旧系统：Legal_Case_Participant 表

独立的参与人表，包含以下人员会自动加入：
- BusinessOwner（业务负责人）
- CaseOriginPeople（案件来源人）
- Investigator（调查员）
- CaseLawyer（经办律师）
- CaseAssistant（律师助理）

每次 CreateUpdate 时先删除全部参与人（`DeleteCaseParticipant`），再重新插入（全量替换模式，和客户共享类似）。

### 新系统：collaborators 字段

新系统在 `business_records.data` 中存储 `collaborators` 数组，没有独立的参与人表。

**待确认**：

- 经办律师、助理等是否自动加入 collaborators？
