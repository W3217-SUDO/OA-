## 根因与修改

| 根因 | 影响接口 | 修改 |

| 读取一笔或少数几笔回款时，旧系统分配金额仍按**全部**可见回款头聚合；发票导出按每 400 个回款分批，每批都全量聚合一次（生产 7 次） | 单笔回款详情、查看分配、分配/退款候选、分配记录、认领/分配锁定、合同回款、发票导出、结算导出、交接投影 | `incoming_source_for` / `payment_conditions`：只聚合实际读取行的回款头 |

## 1.1.493：财务查询缓存按数据修订号失效（`eeae4167`，代码提交 `598d420e`）

### 根因

财务查询的共享缓存（Redis）原以 `pg_current_snapshot()` 作为新鲜度标记。全库任何表的任何提交都会改变该值，生产上财务结果几乎从不命中缓存，每次都重新计算。

### 修改

- 启动迁移 `finance_query_revision_tables_v1`：在除 10 张高频非财务表（`dashboard_change_revisions`、`schema_migrations`、`notification_sync_schedules`、`ipr_case_reminder_types`、`notifications`、`notification_deliveries`、`checkpoints`、`checkpoint_blobs`、`checkpoint_writes`、`checkpoint_migrations`）以外的全部表上安装既有的只追加修订触发器（行级 + TRUNCATE）。只加触发器，不改业务数据。
- 财务查询缓存改用修订日志的 `count:sum` 作为新鲜度标记；任何受覆盖表的写入都会使缓存失效。每次读取都复核覆盖完整性，任何非排除表缺少有效触发器、会话有未提交写入、非 PostgreSQL 或非 read committed 时直接不使用缓存。
- 缓存键仍包含完整身份、全部查询参数、财务中心范围和业务日期。

### 验证

- 本地生产数据副本（4 进程）：28 个接口 × 中心组合的首次计算、缓存命中、修订变化后重算三次返回逐字节一致；排除表写入后缓存保留；真实修改一笔费用金额后立即返回新结果，恢复原文后结果回到原值。
- 定向测试 127 项通过；推送 `dev` 的源码门禁通过。

### 生产核对

- 迁移已执行：350 张表中 340 张带行级与 TRUNCATE 触发器，未覆盖的正好是上述 10 张排除表；服务 active，激活后无错误日志。
- 同一请求连续三次（毫秒，冷 / 热 / 热）：费用查询 7,852 / 7,798（期间有真实写入）/ 13；案件费用退费 7,682 / 48 / 52；内部费用 3,591 / 48 / 13；待结算 5,174 / 23 / 23；待归档 2,622 / 46 / 15；财务概览 1,256 / 18 / 11；三次返回内容一致。
- 数据未变化期间重复打开为 10～50 毫秒；数据有写入后的第一次请求仍按原计算耗时，下表“仍偏慢”项继续优化冷路径。

### 回滚

回滚到 1.1.492 包即可恢复原缓存标记。触发器可保留（只记录修订号）；如需移除，删除非看板依赖表上的 `oa_dashboard_revision_row` / `oa_dashboard_revision_truncate` 触发器并删除 `schema_migrations` 中的 `finance_query_revision_tables_v1`。
